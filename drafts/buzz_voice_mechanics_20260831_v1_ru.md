## Русский драфт

У нас 4 агента работают в общей шине (self-hosted Nostr relay). Каждый профиль отвечает за свой отдел. Правила поведения у всех были прописаны. Проблема: три недели работы шины — и статистика показала, что один из агентов отправил за 7 дней 1 сообщение, а другой за то же время — 55.

Причина не в лени. У профилей не было механики отправки.

Как это устроено у нас:

- Каждый агент — отдельный профиль Hermes со своим nsec (ключ Nostr) в credentials
- Сообщения в шину подписываются ключом отправителя — атрибуция по криптографии, не по имени
- Но команды отправки в профильных инструкциях не было. Агент знал, куда писать и о чём, но не имел рабочего пути доставки

Что настроили (шаги, проверено вживую):

1. **Явный sender.** Скрипт доставки требует `--as <профиль>`. Без флага — отказ. Это не бюрократия: 29.08 мы поймали случай, когда ответ одного агента ушёл под ключом оператора. Подпись по умолчанию = способ потерять атрибуцию.
2. **Верификация доставки.** Успех — это не «команда вернула 0». Успех = подтверждение доставки в выводе с ключом получателя. Правило: нет подтверждения — доставку не заявляй. Перепроверь и доложи.
3. **Один скрипт на всех, nsec по профилю.** Общий хелпер читает ключ отправителя из хранилища по имени профиля. Никаких inline-ключей в командах — ключи не попадают в историю shell.
4. **Адресная доставка.** `--to <профиль>` ставит криптографический mention по pubkey — реальное уведомление адресата. Текст `@Имя` в начале — только для читаемости людьми.

Отдельная грабля — двойные ответы. После того как мы включили второй канал доставки (gateway-плагин, инъекция адресованных сообщений в Telegram-сессию профиля), агенты начали отвечать дважды: старый роутер независимо запускал сессию профиля на то же сообщение. Фикс: внешние профили помечены `external: true` в конфиге роутера — он их дропает, доставка идёт только через новый канал. Урок: два канала доставки без координации = два ответа на каждое сообщение.

Ловля, которую хочу подсветить: конфиг-поле `external` из YAML молча терялось — загрузчик строил объект данных явным списком полей и новое поле не включил. Юнит-тесты отдельных функций это не поймали. Вскрылось только на живом тесте сквозной доставки. Если добавляешь поле в конфиг — проверь весь путь config → dataclass → filter, не только функции.

Чеклист, если поднимаешь multi-agent шину:
1. Правила поведения ≠ механика доставки. Оба блока нужны в инструкции агента
2. Подпись сообщений — только явно (`--as`), дефолтного отправителя быть не должно
3. Успех = подтверждённая доставка, не exit code 0
4. Ключи — из хранилища по имени профиля, не в командной строке
5. Если у доставки два канала — один из них должен глушить второй для своих сообщений
6. Новое поле конфига проверяй сквозным тестом, не юнит-тестами функций

# OpenSpec — инженерный отчёт

Дата отчёта: 2026-09-05  
Статус: рабочая модель по официальной документации Fission-AI/OpenSpec и проверке заявлений ролика «OpenSpec за 5 минут» (Cola Kamornik, https://youtu.be/-G64qjThDfE).

Источники истины по инструменту:

- репозиторий: https://github.com/Fission-AI/OpenSpec
- пакет: `@fission-ai/openspec` (Node.js ≥ 20.19.0)
- лицензия: MIT
- документация: `docs/overview.md`, `docs/getting-started.md`, `docs/concepts.md`, `docs/writing-specs.md`, `docs/reviewing-changes.md`, `docs/editing-changes.md`

Ролик использован только как повод. Ниже — устройство системы, а не пересказ маркетинга.

---

## 1. Что это на самом деле

OpenSpec — слой соглашения между человеком и coding-агентом, реализованный как:

1. набор Markdown-артефактов в репозитории;
2. CLI (`openspec …`) для установки, конфига, статуса, слияния;
3. slash-команды (`/opsx:…`) внутри уже выбранного ИИ-ассистента.

Это не компилятор, не рантайм, не тестовый фреймворк и не замена code review. Код по-прежнему пишет модель. OpenSpec меняет **вход** модели: вместо плавающего чата ей дают папку с намерением, дельтой поведения, дизайном и чеклистом.

Формула, которая соответствует коду и докам, а не слоганам:

> Сначала зафиксировать наблюдаемое поведение, которое должно стать истинным. Потом генерировать код. Потом сверить код со спекой. Потом влить дельту в библиотеку текущего поведения.

Если любой из этих шагов пропускается, OpenSpec деградирует до «ещё одна папка Markdown».

---

## 2. Чего это не делает

Прямо, без оговорок:

- Не делает модель дисциплинированной. Делает невыполнение плана более заметным.
- Не устраняет галлюцинации. Сужает пространство, в котором они живут.
- Не заменяет тесты, типы, линтеры, CI, security review.
- Не описывает всю систему заранее. Основная библиотека спек растёт только тем, что уже архивировали.
- Не является контрактом с юридической силой. Артефакты живые: их правят в любой момент. Документация сама это говорит: «artifacts are the live plan, not a signed contract».
- Не гарантирует, что `archive` сохранит правду, если параллельные изменения трогают одно и то же требование. Archive делает replacement на уровне requirement. Перекрытие даёт потерю сценариев — это уже ловили в самом репозитории OpenSpec (ручной merge overlapping changes).
- Не окупается на задаче «поправь опечатку / напиши скрипт на 15 минут».

Утверждение ролика «непредсказуемая нейросеть превращается в дисциплинированного исполнителя» — ложное как закон, полезное как направление.

## 3. Две оси системы

### 3.1. Библиотека истины: `openspec/specs/`

Описывает, **как система ведёт себя сейчас**, не «как мы когда-то мечтали».

Организация по capability / домену:

```
openspec/specs/
  auth/spec.md
  payments/spec.md
  ui/spec.md
```

Спека состоит из:

- требований в форме наблюдаемого поведения (`SHALL …`);
- сценариев (Given / When / Then или эквивалент).

Спека **не** должна содержать:

- имена классов и функций;
- выбор библиотеки;
- пошаговый план реализации.

Это уходит в `design.md` и `tasks.md`. Смешение слоёв — самая частая порча процесса: спека превращается в простыню реализации и перестаёт быть контрактом поведения.

### 3.2. Единица работы: `openspec/changes/<name>/`

Одно изменение = одна папка = один кусок поведения.

```
openspec/changes/add-dark-mode/
  proposal.md      # зачем и что в скоупе / вне скоупа
  specs/<domain>/spec.md   # дельта, не полная перепись мира
  design.md        # как технически, для нетривиальных изменений
  tasks.md         # атомарные шаги реализации
  .openspec.yaml   # метаданные изменения (schema, флаги вроде retire_capabilities)
```

После завершения папка уезжает в:

```
openspec/changes/archive/YYYY-MM-DD-add-dark-mode/
```

а дельта вливается в `openspec/specs/`.

Инициализация проекта (`openspec init`) поднимает каркас `openspec/` плюс адаптеры под обнаруженные агенты (Cursor, Claude Code, Copilot и т.д.). С v1.0 старые генерируемые `project.md` / `AGENTS.md` / `.cursorrules` как обязательный продукт init больше не являются ядром модели. Ролик, который ставит `project.md` + `idea.md` в центр архитектуры, описывает упрощённую или устаревшую схему.

## 4. Дельта-спека — единственная нетривиальная идея

Внутри change пишется не «вся спека заново», а три класса правок:

| Секция | Смысл | Что делает archive |
|---|---|---|
| `## ADDED Requirements` | нового поведения не было | дописывает в main spec |
| `## MODIFIED Requirements` | поведение было и меняется | **целиком заменяет** старое требование |
| `## REMOVED Requirements` | поведение уходит | удаляет из main spec |

Нюансы, которые ролик опускает:

1. `MODIFIED` требует полную новую редакцию требования, не патч-строку. Неполная замена = тихая порча библиотеки истины.
2. Удаление последнего требования capability не удаляет файл само. Нужен флаг `retire_capabilities: true` в `.openspec.yaml`. Иначе archive останавливается.
3. Retire отказывается работать, если в файле остался мусор вне title / Purpose / requirement-блоков (`## Notes` и т.п.).
4. Несколько активных change, которые правят одно и то же требование, при последовательном archive затирают друг друга. Автослияния сценариев нет. Это ограничение модели, не баг «у вас кривые руки».

Зачем дельта нужна технически: в контекст модели кладётся узкий diff поведения + текущие tasks + при необходимости кусок design. Это дешевле и чище, чем «прочитай весь репозиторий и угадай». Экономия токенов здесь следствие, не цель.

## 5. Команды: две поверхности, одна путаница

Это единственное, что действительно нужно запомнить с первого дня.

| Где | Что | Примеры |
|---|---|---|
| Терминал | установка, каркас, конфиг, инспекция | `npm i -g @fission-ai/openspec@latest`, `openspec init`, `openspec update`, `openspec status`, `openspec config …` |
| Чат агента | рабочий цикл | `/opsx:explore`, `/opsx:propose`, `/opsx:apply`, `/opsx:verify`, `/opsx:archive` |

Префиксы плывут по инструментам (`/opsx:propose`, `/opsx-propose`, `@opsx-propose`). Суть одна: команда исполняется скилом агента, который читает файлы change и пишет в них / в код.

### Профиль `core` (по умолчанию)

```
/opsx:explore   → думать, ещё без папки change
/opsx:propose   → создать папку и черновики артефактов
[ревью плана человеком]
/opsx:apply     → реализовать tasks.md
/opsx:verify    → сверка кода с артефактами (часто пропускают)
/opsx:sync      → синхронизация дельт в main specs без полного archive
/opsx:archive   → merge дельт + перенос папки в archive
```

### Расширенный профиль

`/opsx:new`, `/opsx:continue`, `/opsx:ff` (сразу все planning-артефакты), `/opsx:bulk-archive`, `/opsx:onboard`.

`propose` в core ≈ «создай change и сразу набросай артефакты». Это не священный водопад. Документация прямо называет артефакты *enablers, not gates*: можно поправить `design.md` посреди apply и продолжить. Цена свободы — дисциплина скоупа. Без неё change расползается в «ещё один чат, только в файлах».

## 6. Где в цикле сидит инженерная работа

OpenSpec честно выделяет два момента ревью. Оба обязательны. Ролик подробно говорит только про первый.

```
propose → РЕВЬЮ ПЛАНА → apply → РЕВЬЮ КОДА / verify → archive
           дешёвая ошибка              дорогая ошибка
```

Порядок чтения change (из `docs/reviewing-changes.md`):

1. `proposal.md` — если скоуп кривой, дальше не читать.
2. delta specs — сердце: определено ли «готово» сценариями, которые вам было бы обидно сломать.
3. `design.md` — только если изменение нетривиальное.
4. `tasks.md` — атомарны ли шаги, нет ли скрытого рефакторинга «заодно».

После apply правило reconciliation:

- код верный, спека устарела → сначала честно поправить дельту, потом archive;
- спека верная, код уехал → чинить код, не подгонять истину под дрейф.

Архивация без этой сверки записывает ложь в `openspec/specs/`. Дальше каждый следующий агент будет добросовестно воспроизводить ложь.

`/opsx:verify` — не доказательство корректности. Это ещё один проход модели по артефактам и коду. Полезно как чеклист расхождений. Бесполезно как замена теста.

## 7. Сравнение с тем, что сказал ролик

| Тезис ролика | Факт |
|---|---|
| Центр системы — `project.md`, `idea.md`, `design.md`, `tasks.md` | Центр — `openspec/specs/` (поведение сейчас) + change с `proposal.md` / delta specs / `design.md` / `tasks.md`. `idea.md` в каноне нет. `project.md` не ядро после v1.0 |
| Конвейер Pros → Apply → Archive железный | Имена: Propose / Apply / Archive. Порядок рекомендуемый, не жёсткий. Есть explore, verify, sync, update, ff, continue |
| Идеально для brownfield | Да, в этом и смысл дельт. Для greenfield тоже работает, но не в этом преимущество |
| Легче Spec Kit | В целом верно: меньше фаз, нет обязательного Python-стека, быстрее старт. Цена — меньше формальной принудительности |
| Спека станет единственным рукописным артефактом | Гипотеза, не свойство инструмента. Пока спеки тоже пишет модель, и их тоже надо читать |
| 5 минут на понимание / внедрение | Init — минуты. Рабочий навык — писать узкие требования и не врать в archive. Это недели привычки |
| Агент не прыгает через tasks | Он *должен* идти по чеклисту. Фактически прыгает, если человек не смотрит diff и не режет скоуп |

## 8. Ограничения, которые нужно закладывать в процесс

1. **Качество входа.** Расплывчатый propose даёт аккуратно оформленную расплывчатость. Фреймворк не добавляет вкуса к границам системы.
2. **Дрейф спека ↔ код.** Без verify и тестов библиотека истины гниёт быстрее, чем чат.
3. **Параллельные change.** Requirement-level replace. Пересечения решать руками до archive, не после.
4. **Модель-зависимость.** Слабая модель хорошо заполняет шаблоны и плохо держит инварианты. OpenSpec усиливает сильную модель и слабо страхует слабую.
5. **Телеметрия.** В CLI по умолчанию включена. Выключается: `openspec config set telemetry.enabled false` или `OPENSPEC_TELEMETRY=0`.
6. **Stores (общий репозиторий спек на несколько репо)** — отдельная, ещё сыроватая ось. Не путать с локальным `openspec/` в одном проекте.
7. **Объём спек.** Доки сами предупреждают: полная строгость — для рискованных изменений. Большинство change должны оставаться короткими. Простыня на 2 000 строк убивает и человека, и контекст модели.

## 9. Когда инструмент окупается

Окупается, если одновременно верно несколько условий:

- изменение переживёт больше одной сессии или больше одного агента;
- цена «сделали не то» выше цены написать две страницы Markdown;
- в репозитории уже есть нетривиальные инварианты (auth, деньги, очереди, совместимость API, UI-контракты);
- кто-то реально читает proposal и дельту до apply.

Не окупается, если:

- задача умещается в один очевидный diff;
- никто не будет ревьюить артефакты (тогда это бюрократия);
- «спека» пишется после кода для галочки перед archive;
- проект — набор разрозненных скриптов без устойчивого поведения.

Минимальный рабочий контур без религии фреймворка, если CLI не нужен:

1. Зафиксировать «что должно стать истинным» и «что ломать нельзя».
2. Разрезать работу на шаги, которые можно отметить.
3. После кода сверить поведение с пунктом 1.
4. Сохранить это рядом с кодом, не в чате.

OpenSpec автоматизирует именно этот контур и добавляет merge дельт. Полезность = автоматизация + общее место. Магия = 0.

## 10. Рабочий минимум, если внедрять

```bash
# терминал
npm install -g @fission-ai/openspec@latest
cd <repo> && openspec init
openspec config set telemetry.enabled false   # если не нужны их метрики
```

В чате агента:

```
/opsx:explore          # если скоуп ещё неясен
/opsx:propose <slug>   # получить папку change
# прочитать proposal.md и specs/ — это и есть работа
/opsx:apply
/opsx:verify           # не считать доказательством, считать списком дыр
/opsx:archive          # только когда дельта честно описывает то, что уехало в код
```

Критерий, что процесс живой, а не декоративный:

- в `openspec/specs/` после месяца работы есть поведение, которое агент реально использует как ограничение;
- archive не делается в ту же минуту, что apply;
- хотя бы раз план отклоняли до кода.

Если этого нет, OpenSpec установлен, но не используется.

## 11. Вывод

OpenSpec — файловый протокол для coding-агентов: отделяет текущее поведение системы от незавершённого изменения, заставляет писать дельту наблюдаемого поведения до кода и даёт механику вернуть эту дельту в общую библиотеку.

Сильная часть — дельта + изоляция change + дешёвое ревью плана.  
Слабая часть — вера, что наличие папок равно контролю. Контроль появляется только если человек отбраковывает плохой план и не архивирует расхождение.

Ролик правильно ставит диагноз vibe coding и неправильно продаёт прогноз «хаос кончился». Хаос кончается в том же месте, где он кончался до ИИ: на явном инварианте и на человеке, который проверяет, что инвариант ещё жив.

Черновик:

SPA-фоллбек отдавал index.html со статусом 200 на любой незнакомый путь, включая имена исходников. Deny-правило `location ~* \.bak$ { deny all; }` не ловило timestamp-суффикс.

1) Что случилось

На одном из моих проектов — self-hosted мессенджер на собственном VPS — в nginx стояло правило `location ~* \.bak$ { deny all; }`. Логика: не отдавать наружу бэкап-файлы с исходниками. При самостоятельной перепроверке VERIFIED-отчёта я заметил: правило матчит `config.bak`, но не матчит `config.bak.0816_0105` — а деплой-скрипт создаёт бэкапы именно с timestamp-суффиксом.

У сайта был SPA-фоллбек — «если файл не найден, отдай index.html». Проверка curl показала, что `receiver.py`, `kpz_bot.py`, `goolag_notify_bot.py`, `operators/*.py` — полный код бэкенда — отдавались наружу со статусом 200. Правило `.bak$` само по себе матчит `config.json.bak`, но порядок location: до deny-правила запрос попадал в SPA-фоллбек, если файла нет на диске; лежащий файл отдался бы как есть.

2) Как это работало

Сканеры в access-логах получали 200 на `/settings.py` и подобные пути — но это был HTML-фоллбек, файла на диске не существовало. Эксплуатируемой утечки это правило не создавало — но и защиты не было: любое имя файла, попавшее на диск, становилось доступно.

Фикс в конфиге: `location ~* \.(py|sh|bak\.[0-9]+.*|bak-[0-9].*|bak)$ { deny all; }` плюс `location ^~ /operators/ { deny all; }`, reload. Curl-верификация: все .py/.bak/.sh/operators → 403; index.html, css, assets, рабочий config.json → 200; health-эндпоинт жив — клиент не задет.

3) Свой опыт

Я прошёлся по access-логам (rotated включительно). По маскам сканеры и правда ловили 200 — но по реальным именам файлов (`receiver.py`, `operators/`, `*.bak.`) внешних скачиваний нет.

Вторая находка той же проверки: инвентаризация показала «4 старых bak». Реально на проде было 20 bak-файлов плюс 2 каталога (период 0721–0816) — плюс 8 bak-конфигов nginx плюс два хвоста самого фикса, world-readable и с путями к секретам. Снесено в тот же день (22 файла web-root + 2 каталога + 8 конфигов + два хвоста фикса), `nginx -t` OK, негативный smoke: старые пути → 403.

Отдельный урок того же дня. Система промолчала: сервис поднялся без секретов, `email_sent=False`. Поэтому deploy-скрипт получил fail-loud гейт — удалённый `test -s` на файлы секретов, `DEPLOY ABORT` до любого рестарта; отсутствие SMTP-кредов поднимает ValueError. Негативные прогоны на живом проде: нет хоста → ABORT, нет секрета → ABORT, всё на месте → rc 0. Следующий деплой прошёл через гейт штатно.

4) Вывод

Два урока. Первый: статус 200 ничего не говорит о содержимом — SPA-фоллбек превращает «файла нет» в «отдаю HTML с успехом». Проверяйте логи по реальным именам файлов, не по статусам. Второй: система, которая может промолчать, промолчит — поэтому гейты, которые роняют деплой при отсутствии критического файла, дешевле тихой иллюзии.

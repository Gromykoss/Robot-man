Нашли OpenSpec — слой спецификаций для coding-агентов (Fission-AI): не чат, а файлы. Ролик «за 5 минут» бьёт в боль vibe coding: новый чат = чистый лист, модель забывает вчерашние правила и по «поменяй кнопку» переписывает полсистемы.

Решение, которое они продают: `openspec/specs/` = как система ведёт себя **сейчас**; `openspec/changes/` = песочница одной фичи; цикл propose → ревью плана → apply → archive. Дельта ADDED/MODIFIED/REMOVED, чтобы не переписывать простыню. Тренд тот же, что у всех, кто устал от чата: поведение рядом с кодом, не в истории вкладки.

Мы не ставили это как религию CLI. Мы взяли **идеи** и за один день прогнали на своём WhatsApp-боте стройки — там, где у агента уже было 148 markdown-файлов «документации».

## Что было

148 `.md`. При баге агент чинил код по интуиции. Спеки гнили и расходились с git. Документация не была входом сессии — была свалкой.

## Что сделали (идеи OpenSpec → наш contract-index)

**Слой 1.** `PROJECT_MEMORY_GRAPH.md` — 47 строк. Обязательный boot каждой сессии. Инварианты, карта доменов, куда идти за deep docs. Большие файлы на старте не читаются.

**Слой 2.** 9 доменных карточек в `openspec/specs/`: роль, owners, traps, GIVEN/WHEN/THEN. Задача про домен → сначала карточка.

**Слой 3.** MASTER_SPEC, DATA_CONTRACT, код — только по маршруту карточки.

В AGENTS.md — gate: deep docs через карточку; после смены домена обновить граф/карточку или записать `Contract index update: not needed`.

~45 файлов ушли в архив. В корне остался короткий набор из **16** entry-.md.

## Что всплыло, когда docs сверили с git (не с чатом)

**Фантом.** `ojr_sync.py` описан в INDEX / MASTER_SPEC / RUNBOOK. В git модуль никогда не появлялся (0 add-коммитов). Роль давно в `db.py` и `whatsapp_commands.py`. Свалка md держала имя файла, которого не было.

**Петля.** post-commit hook писал CHRONOLOGY на каждый коммит, включая коммиты `chrono:…` о самих записях: `6281db7 → 2cbe1d3 → 6685fc9 → 3a4d262`. Guard: `chrono:*` → exit 0.

**Пилот карточки не на бумаге.** Домен vor-import — реальный прогон справочника: 573 кода · 0 insert · 573 update · 0 conflict · 573 unique · 554 с ценой. Baseline вписали в карточку.

Graph view: 127 заметок с вики-связями + canvas 126 узлов / 141 ребро.  
Сверка: Grok 4/4 PASS · 36/36 путей на диске · review scope 45 passed.

## Что поняли про сам OpenSpec (после сверки с доками, не только с роликом)

Сильная часть — та же, что сработала у нас: отделить **текущее поведение** от **незавершённого change**, ревьюить план до кода, не грузить агенту всю свалку.

Слабая часть ролика: «непредсказуемая сеть → дисциплинированный исполнитель» — не закон. Модель всё равно прыгает через tasks, если человек не смотрит diff.  
`project.md` / `idea.md` как центр — упрощение; в актуальной модели ядро = `specs/` + change.  
Archive без сверки кода и дельты записывает ложь в библиотеку — дальше агенты её честно воспроизводят.  
MODIFIED в дельте — полная замена требования, не патч-строка; параллельные change на одно requirement затирают друг друга.

Окупается, когда изменение переживёт сессию и кто-то читает plan до apply. На опечатке и «спека после кода для галочки» — бюрократия.

### 1. Shadowban Diagnostic
- `x_search from:RobotsTJ500` + `get_users_posts` (5 последних)
- Impressions delta vs 7-day baseline
- Признаки: 0 impressions на RT, <20 на оригинальный пост, посты не в поиске

### 2. Content Performance
- Все посты за 7 дней: impressions, likes, replies, reposts, dwell estimate
- Победитель (max engagement rate) и проигравший
- Паттерны: какой формат/тема/время дали лучший результат

- Mutuals: сколько, релевантность (keyword match), engagement rate

- Отток: сколько ушло

### 4. Engagement Activity
- Replies sent, likes given, reposts
- Reply rate на наши посты (% comments answered)
- Quality: не шаблонные, contextual

### 5. Timing Analysis
- Лучшее окно за 7 дней (UTC)
- Худшее окно
- День недели с max impressions

### 6. Risk Assessment
- Shadowban риск
- Spam риск (частота, шаблонность)
- Toxicity риск (посты которые могут задеть аудиторию)

- Ключевые аккаунты: что постят, engagement
- Тренды: темы которые набирают обороты

## Принципы

1. **Data > intuition.** Каждое тактическое решение основано на цифрах за 7 дней.
2. **Graduated, not binary.** Не «постим/не постим», а уровень риска и соответствующий уровень агрессии.
3. **Чистота сигнала.** Не размывать mutual graph, не постить filler, не использовать шаблоны.
4. **Feedback loop.** Результат каждого дня → анализ следующей ночью → коррекция тактики.
5. **Одна рука знает что делает другая.** Nightly Analysis → TACTICS.md → все кроны читают его.

# Диагностика теневого бана X/Twitter

## Когда применять
Резкое падение просмотров (с 100-200 до 5-8) при неизменном качестве контента.

## ⚠️ ВАЖНО: сначала официальные правила, потом народные советы (урок 31.07.2026)

Корень теневого бана бот-аккаунта чаще всего — НАРУШЕНИЕ официальных правил, а не «злой алгоритм»:

1. **Метка «automated» ОБЯЗАТЕЛЬНА** для всех ботов на X API (docs.x.com/developer-guidelines). Нет метки = X фильтрует посты из поиска.
   - Ставится ТОЛЬКО вручную: Settings → Your account → Your account information → Automation → Managing account
   - API для метки НЕТ.
2. **Авто-лайки ЗАПРЕЩЕНЫ** правилами автоматизации.
3. **Авто-реплаи по keyword search ЗАПРЕЩЕНЫ** — только опт-ин (юзер сам ответил/написал).
4. **Bulk follow/unfollow ЗАПРЕЩЁН.**
5. Источник: help.x.com/en/rules-and-policies/twitter-automation.html (апрель 2026).

Порядок диагностики: официальная политика → посты сообщества → своя история. Не начинать с народных средств.

## Процедура

### Шаг 1 — Проверить поиск
```bash
x_search "from:USERNAME"
```
Если «No public posts were found» — shadowban подтверждён.

### Шаг 2 — Проверить прямые ссылки
```bash
curl -s -o /dev/null -w "%{http_code}" "https://x.com/USERNAME/status/POST_ID"
```
200 = пост жив, но не индексируется.

### Шаг 3 — Проверить ключевые слова
```bash
x_search "USERNAME topic keyword"
```
Если Grok находит пост по словам но не по `from:` — search shadowban.

### Шаг 4 — Проверить reply deboost (самая частая форма в 2026)
С search-баном путают подавление ответов: реплаи живы, но скрыты под «Show more replies» у не-фолловеров.
```bash
# С чужого аккаунта (logged-out/инкогнито) открыть пост популярного аккаунта,
# куда мы реплайнули. Если наш ответ под "Show more replies" или не виден — reply deboost.
```
Признак: охваты постов в норме, но engagement с чужих аккаунтов ~0, реплаи никто не видит.

### Шаг 5 — Сверить с официальной политикой поиска
help.x.com/en/rules-and-policies/twitter-search-policies: X фильтрует из поиска за
повторяющийся контент, злоупотребление хэштегами, авто-посты/авто-реплаи, похожие сообщения с нескольких аккаунтов, агрессивный follow/unfollow.
Если наш аккаунт делал хоть одно из этого — фильтр ожидаем, лечим поведением (не «злым алгоритмом»).

## Причины (по вероятности)

1. **Self-reply** — ответ на свой же пост
2. **ALL CAPS заголовки** — спам-паттерн
3. **Авто-реплаи с шаблонами** — Reply Engine
4. **Высокая частота автоматизации** — много действий без органики
5. **Низкий engagement** — X считает контент неинтересным

## План восстановления

1. Пауза X-фейсинговых cron'ов: Reply Engine, Content Post, Engagement
2. 3-5 дней тишины
3. Ручная активность с аккаунта (лайки, 1-2 реплая в день)
4. Пересмотр автоматизации: реже + без шаблонов

## Pitfalls
- x_search через Grok имеет привилегированный доступ — находит то что обычный поиск не видит
- **xurl search — ТОЖЕ привилегированный, НЕ тест бана (доказано 04.08.2026):** xurl search "from:USERNAME" возвращал 3 поста (включая свежий) при живом бане — обычный поиск в мобильном приложении (вкладка «Последние») показывал 0. Единственный честный тест — публичный поиск x.com в инкогнито/незалогиненном браузере или телефоне, вкладка Latest, искать `from:USERNAME`.
- X MCP требует bookmark.write scope для удаления закладок

# Startup Radar Protocol — молодые проекты агентной тематики

Утверждено Сергеем 25.08.2026 после кейса ZaGuu (позвал в треде → сыграли 3 матча → war-story пост → reply создателю). Цикл повторяем для новых проектов.

## Что ищем

Молодые стартапы/платформы, где наш агент может ДЕЙСТВОВАТЬ, а не только читать про них:
- арены игр для агентов (ZaGuu, Arena42)
- соцсети агентов (Moltbook, AgentFlex)
- бенчмарки с live-API (не статические)
- инструменты с agent-facing API / skill.md

**Фильтр релевантности:** тематика X-аккаунта = агентная инженерия. Проект должен давать историю «наш агент сделал X».

**Цель цикла — взаимное маркетинговое продвижение:** проекту — кейс и упоминание; нам — история для сериала «строим на публике», контакт с билдерами, их аудитория.

## Конвейер (7 этапов — роли Сергея и Robot-man)

1. **Команда Сергея: «ищем перспективные проекты»** → я сканирую радаром (web_search, x_search, Product Hunt, треды), отбираю **3 интересных кандидата** и даю **краткое самари по каждому**: что это, стадия, чем интересно нашему агенту, какой контент выйдет, риски в одну строку.
2. **Сергей выбирает кандидата** → углублённое исследование СНАРУЖИ: что за проект (первоисточники: skill.md/docs/README), как регистрироваться, как участвовать, экономика, авторы. Риски — отдельным блоком. Без регистрации.
3. **Регистрация (Сергей и/или я)** → после неё исследование ИЗНУТРИ: реальный онбординг, интерфейсы, где живут данные, что видят другие участники. owner_email Сергея — только спрашивая. Сторонний npm CLI — проверка пакета до установки.
4. **Участие + сбор фидбека** → минимальный цикл: первая игра/задача → результат. Харнес ZaGuu как шаблон (poll loop, фазовая машина, идемпотентность). Все цифры из живого API, скриншоты/JSON в drafts/. Что платформа даёт нашему агенту и что мы ей — фиксирую для поста.
5. **Подписки + чтение их контента.** Подписаться на разработчиков и официальную страницу проекта, прочитать их свежие посты — их формулировки и акценты идут в материал для нашего поста (что они сами считают главной фичей).
6. **Публикация поста с упоминанием разработчиков.** Полный постовой протокол: RU драфт (рабочий) → Grok Build + MoA → EN ФИНАЛ → факт-гейт CONTENT_BRIEF.md → обложка (сцена Grok Build + MCV) → чеклист → approval → post_with_log.sh с mentions разработчиков.
7. **Мониторинг взаимодействия.** Следить за ответами на пост, отвечать вежливо и по делу (reply через `xurl reply`, не standalone), благодарить без дословного цитирования Сергея. Лимит 3 public writes/сутки.

**Итог цикла: взаимное маркетинговое продвижение** — проект получает кейс и упоминание, мы получаем историю «строим на публике», контакт с билдерами и аудиторию их комьюнити.

# Evidence-Based Reporting — правила анализа для Сергея

## Главное правило

Любое утверждение требует доказательств. Нет данных → «недостаточно данных», не домысел.

## Язык отчётов (29.07.2026)

**Все отчёты для Сергея — на русском.** Коротко, без английского жаргона. Если отчёт крона пришёл на английском — переведи, сократи, покажи суть. Термины (shadowban, API, cron) можно оставить на английском — вокруг них строится рабочий контекст. Но сам текст отчёта — русский.

**Реальный кейс:** Nightly Analysis пришёл на английском с 50% терминов. Пользователь: «столько терминов на английском, 50% почти, читать невозможно, можешь человеческий отчёт давать?»

## Формат ответа Сергею

- Сначала цифры, потом выводы
- Русский язык, короткие фразы, без маркетинга
- «+2 подписчика (407→409). Идентифицирован: @username. Второй — неизвестен (нет снапшота)»
- Не «бот» без доказательств
- Не «X делает X» без ссылки

## Ревизия / ops-доклад Hermes (05.09)

Когда нужен status pack (аккаунты + cron + docs + delivery):
1. Live tools this turn only — no memory-only claims.
2. After claiming Hermes fixed X — **re-read** jobs.json `enabled` + file headers.
3. Ban language: prefer Sergey Latest/incognito over Nightly self-report (CP-13: 2+ independent signals).
4. final-send NOT suppressed + streamed=False = known-noise (not duplicate incident) per Hermes RCA 05.09.
5. Sample bus report: `buzz-agent-bus-communication/references/hermes-revision-report-20260905.md`.

## CHRONOLOGY Agent — не доверяй слепо (29.07.2026)

**Правило:** записи CHRONOLOGY Agent проверять через live-инструменты перед тем как на них полагаться. Не `x_search` (xAI, привилегированный доступ), а скраперы (`xactions search`, `twitter search`) — только они показывают реальную публичную картину.

**Реальный кейс:** CHRONOLOGY Agent записал «shadowban снят, 9 результатов». CONTENT_BRIEF был построен на этой записи. Факт-чек через `xactions search "from:RobotsTJ500"` → **0 результатов**. Shadowban НЕ снят. CHRONOLOGY Agent ошибся. Запись откачена, брифинг аннулирован.

**Процедура верификации:**
1. Получил отчёт крона → НЕ действуй сразу
2. Проверь ключевые утверждения через live-инструменты
3. Если скраперы недоступны (сессия отвалилась) — скажи об этом, не домысливай
4. Если данные крона расходятся с живой проверкой → живая проверка ПРИОРИТЕТНЕЕ

## Анализ подписчиков

### Не называй ботом без явных признаков

Сигналы которые НЕ доказывают бота:
- Дефолтная аватарка — новички не настраивают профиль
- 0 твитов — аккаунт мог быть создан сегодня
- Подписки на крипту — живой интерес многих людей
- Непонятное описание профиля

⚠️ **Каждый новый запрос — новая проверка.** Не кэшируй старые предположения.

Явные признаки бота:
- Спам-твиты с phishing-ссылками
- Mass-follow паттерн (>100/день)
- Группа аккаунтов с одинаковыми описаниями
- Генераторные username'ы (user38472947)

## Необъяснённая запись/пост = задача forensics, не домысел (25.08)

**Правило:** когда отчёт крона находит артефакт без объяснения (пост без метрик, ID без записи в CHRONOLOGY) — это задача расследования через перекрёстные источники, НЕ повод гадать «возможно, удалён». Порядок:

1. **API-статус:** `xurl read <ID>` — «Could not find post» = пост удалён или не существует.
2. **Локальный лог:** grep ID по `published_posts.jsonl` — есть запись = публикация реально проходила через post_with_log.sh (ID вернул xurl).
3. **История сессий:** `session_search(query="<ID>")` — восстановить ЧТО это был за пост и ПОЧЕМУ исчез (удалён вручную? ошибочный standalone?).
4. **Git-история** репо вокруг времени события + `write_counter.json`.
5. Только после реконструкции — дописать пропущенную запись в CHRONOLOGY задним числом с пометкой.

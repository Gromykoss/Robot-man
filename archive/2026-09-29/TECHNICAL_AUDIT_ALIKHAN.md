## 1. АРХИТЕКТУРНЫЙ АНАЛИЗ

### 1.1. Текущая архитектура

```
WhatsApp → Hermes Bridge (:3000) → bridge_wrapper.py → main_waha.py (3s polling)
  ├─ Sandbox цикл (120363179621030401@g.us):
  │   ├─ QA Parser (qa.py) — VOR regex + Grok JSON
  │   ├─ Router (router.py) → CMD/QA/RESIDUAL/WEATHER/DB/GROK/IGNORE
  │   ├─ Poll Module (poll.py) — start→parse→status→close
  │   ├─ EJO Generator (fill_ejo.py) — weather + QA → 3-sheet XLSX
  │   ├─ Daily Snapshot (generate_daily_snapshot) — фото+сообщения+QA+ЕЖО+погода
  │   └─ Calendar Reminders (background thread, 60s)
  │
  ├─ Production listener (120363400682390076@g.us):
  │   └─ Только захват: фото→Grok Vision, документы→DB, текст→QA parse
  │
  └─ Инфраструктура:
      ├─ Hermes Bridge (WhatsApp WebSocket)
      ├─ PostgreSQL (evolution-postgres :5432, таблицы: bot_memory_*, bot_poll_*, bot_schedule_*)
      ├─ xAI Grok-4 (vision + force_grok queries)
      ├─ Ollama qwen2.5:14b (локально, текстовые задачи)
      ├─ Open-Meteo API (погода)
      └─ wttr.in (погода, fallback)
```

### 1.3. Оценка архитектуры — 6.5/10

**Сильные стороны:**
- Модульная декомпозиция (QA, poll, fill_ejo разделены)
- Двухэтапный QA-парсер (regex → Grok) исключает галлюцинации VOR-кодов
- Bridge wrapper v2 с буфером решает race condition /messages
- LLM-роутер с fallback Ollama→Grok экономит токены

**Слабые стороны:**
- `main_waha.py` (1152 строк) — God-объект: обработка команд, снимок дня, слушатели, календарь
- Дублирование: `send_msg` в трёх файлах, `cmd_words` в двух, `SIM_DATE` в двух
- Нет централизованного конфига — константы разбросаны по модулям
- Нет Dependency Injection — модули импортируют друг друга циклически (fill_ejo→db, main_waha→fill_ejo→db)
- `daily_snapshot.py` — мёртвый код, не используется (снимок дня встроен в main_waha.py)

## 3. ПРОБЛЕМЫ С ДАННЫМИ

### 3.1. Негативные факты

**Проблема:** `close_poll()` (poll.py:520-531) авто-заполняет отсутствующие категории негативными фактами:
- «Бетонирование не выполнялось»
- «Монтаж не выполнялся»
- «Земляные работы не выполнялись»
- «Поставок материалов нет»

**Риски:**
- Эти факты сохраняются с `source='auto'`, но poll.py пишет их в `bot_memory_facts` без поля `source`
- Категории жёстко закодированы — новые категории будут пропущены
- Снимок дня исключает негативные факты (`fact NOT ILIKE '%не выполня%'`), но другие потребители могут их подхватить

### 3.2. Теги фото

**Текущее состояние:** Тег `building` присваивается по ключевым словам в caption сообщения. Если caption: «фото АБК» → building='АБК'. Иначе → building='без тег'.

**Проблемы:**
- Фото без тега попадают в «Общий план» при подсчёте — искажает статистику (photos():464)
- Нет механизма ручной корректировки тегов
- Старые фото (до 15.07.2026) не имеют тегов вообще
- `db_memory.py::get_untagged_messages()` есть, но нигде не вызывается

### 3.3. Poll state

**Текущая схема:** `bot_poll_state` (id, chat_id, poll_date, status, started_at, closed_at) + `bot_poll_residuals` (id, poll_id, code, building, name, unit, plan_volume, residual_volume, actual_today).

**Проблемы:**
- `bot_poll_state` имеет UNIQUE(chat_id, poll_date) — только один опрос в день. Не позволяет перезапустить сломанный опрос (ON CONFLICT DO UPDATE перезаписывает)
- `bot_poll_residuals` не хранит `residual_volume` — столбец есть в схеме, но `_get_work_items_from_template()` ставит `ostatok` в оба поля (`plan_volume` и `residual_volume`) — семантически неверно
- Никаких внешних ключей на `chat_id` → нельзя отследить какой группе принадлежит опрос

### 3.4. Погода

**Текущее:** Два источника — wttr.in (основной) + Open-Meteo (fallback). Используется в `fill_ejo.py::weather()` и `daily_snapshot.py::get_weather()` и `generate_daily_snapshot()`.

**Проблемы:**
- `fill_ejo.py::weather()` использует ТОЛЬКО Open-Meteo, без wttr.in fallback
- `daily_snapshot.py::get_weather()` использует ТОЛЬКО wttr.in, без Open-Meteo fallback
- `generate_daily_snapshot()` использует wttr.in → Open-Meteo — единственная корректная цепочка
- Разные форматы вывода погоды в разных местах
- `daily_snapshot.py` не использует `lang=ru` для wttr.in — погода может быть на английском

## 4. ОЦЕНКА КАЧЕСТВА СНИМКА ДНЯ И ЕЖО

### 4.1. Снимок дня — 7.0/10

**Сильные стороны:**
- Собирает данные из 6 источников: фото (БД), документы, сообщения, QA-факты, ЕЖО/опрос, погода
- Двойной fallback погоды (wttr.in → Open-Meteo) в `generate_daily_snapshot()`
- Корректный timezone (Бишкек UTC+6) с range-запросами
- Фото RAW из БД без реинтерпретации через LLM
- Исключение негативных QA-фактов

**Слабые стороны:**
- Сложный JOIN-запрос к `bot_poll_residuals` привязан к структуре БД
- Коды работ ищутся через `load_workbook` на каждый вызов (тяжело)
- Нет кеширования code→name маппинга
- Промпт (строки 206-235) собирается вручную, а не через структурированный шаблон из `bot/prompts/`
- `daily_snapshot.py` существует параллельно и не синхронизирован

### 4.2. ЕЖО — 7.5/10

**Сильные стороны:**
- Три листа: «Ежедневный отчет», «Персонал и техника», «Материалы и планы»
- Правильная цепочка кумулятивов: prev_P + v → P, prev_S + v → S
- Авто-обновление шаблона из пользовательских правок
- Фото в основном листе (строки 856-859) вместо отдельного листа
- Жёлтая заливка только для строк с объёмами
- Процент готовности (K853) с учётом ПСД (6%)

**Слабые стороны:**
- `calc_completion_pct()` использует вес ПСД = 6% — хардкод
- Сложная логика в `fill()`: ~600 строк с глубокой вложенностью
- `_hide_rows()` и inline hide-логика дублируются
- Парсинг персонала через regex хрупкий
- Парсинг материалов неполный — не все форматы охвачены
- Падение `yesterday_cum()` при удалении вчерашнего файла
- Нет валидации выходного файла перед отправкой

## 5. НАДЁЖНОСТЬ, МОНИТОРИНГ, ОТКАЗОУСТОЙЧИВОСТЬ

### 5.1. Текущее состояние — 4.5/10

**Что есть:**
- `health_check.sh` (8 проверок)
- `alikhan_health_check.py` (8 измерений)
- `verify.py` (верификация ответов Grok)
- `test_qa_parser.py` (6 тестов)
- `verify_ejo.py` (сравнение v1 и corrected)
- Pre-commit hook (py_compile + линтер-варнинги)

**Что отсутствует:**
- ❌ **Мониторинг в реальном времени** — нет Prometheus/Grafana, нет алертов
- ❌ **Автоматический перезапуск при падении** — systemd юнит есть, но нет health-check + auto-restart
- ❌ **Алерты при аномалиях** — нет детекции: бот молчит > N минут, дубликаты процессов, очередь моста растёт
- ❌ **Резервное копирование БД** — нет автоматических бэкапов
- ❌ **Graceful degradation** — при падении Ollama/Grok бот молча фейлится
- ❌ **Структурированное логирование** — только `print()` без уровней, ротации, формата
- ❌ **Сбор метрик** — нет счётчиков: сообщений/день, QA-фактов/день, ошибок/день, latency

### 5.2. Критические точки отказа

1. **Hermes Bridge** — единственная точка входа WhatsApp. При падении бот полностью теряет связь.
2. **PostgreSQL** — единственная БД. При падении теряются все сообщения и факты.
3. **xAI API** — при превышении лимитов или падении Grok, vision-фичи и QA-парсинг перестают работать.
4. **Ollama** — локальная LLM, потребляет RAM. При OOM бот падает на fallback к Grok, но не восстанавливается.

   - Визуализация: график готовности проекта, фото с привязкой к зданиям

   - Результат: автоматически сформированный Excel + снимок дня

3. **«Один день из жизни прораба» — сценарий:**
   - 08:00 — Алихан присылает сводку (погода, график, напоминания)
   - 10:00 — Прораб сбрасывает фото в группу → авто-описание + теги
   - 16:00 — Алихан запускает опрос остатков
   - 17:00 — Прораб вводит данные → ЕЖО готов за 30 секунд
   - 18:00 — Снимок дня для руководства

### 7.2. Документация для конкурса

1. **Описание проблемы:**
   - ТЗРК Джеруй — стратегический золоторудный проект Кыргызстана
   - Ежедневная отчётность обязательна (ЕЖО) для подрядчика (АйБиКон → Альянс-Алтын)
   - 800+ кодов работ, 3 подрядчика, 3 здания
   - Ручное заполнение: 2-3 часа → ошибки, задержки, неполнота

2. **Архитектурная схема** (готова в `architecture.md`)

3. **Ключевые метрики эффективности:**
   - Время заполнения ЕЖО: 2-3 часа → 30 секунд (**сокращение в 240-360x**)
   - Ошибки в отчётах: ~15% → <2% (авто-валидация + проверка Grok)
   - Фотоотчёт: ручная вставка → авто-вставка с описанием
   - Языковой барьер: русский/казахский через LLM с авто-переводом

4. **Технические инновации:**
   - Двухэтапный QA-парсер: regex для структурных данных + LLM для свободного текста
   - Vision API для описания фото стройплощадки без предположений
   - Локальная LLM (Ollama) для снижения затрат на API
   - WhatsApp как интерфейс — не требует обучения пользователей
   - Авто-коррекция шаблона ЕЖО через diff

5. **Реплицируемость:**
   - Открытый исходный код
   - Docker-контейнеризация
   - Работает с любым WhatsApp-номером
   - Применимо к любым строительным проектам (не только золотодобыча)
